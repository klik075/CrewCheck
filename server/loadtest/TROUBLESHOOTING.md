## A. 대기실에서 멀쩡한 참가자가 로비로 튕기는 문제

### 1. 문제 상황

WebSocket 실시간 신호를 붙인 뒤, 대기실에 가만히 있던 참가자가 갑자기 로비로 튕기는 현상이 생겼다. 네트워크가 끊긴 것도 아니고 직접 나간 것도 아니었다.

서버는 대기실 참가자가 살아 있는지를 **방 조회(`GET /rooms/{id}`)가 들어온 시각**으로 판단한다. 마지막 조회 후 기준 시간(당시 30초)이 지나면 `RoomPresenceService`가 5초마다 돌며 그 사람을 방에서 뺀다.

### 2. 원인 분석

**조회 주기가 바뀌었는데 기준 시간은 그대로였다.**

| | WebSocket 이전 | WebSocket 이후 |
| --- | --- | --- |
| 방 조회 주기 | 1초 | **15초** (신호가 오면 그때 조회, 평소엔 15초 안전망 폴링) |
| 접속 기록이 남는 경로 | 방 조회 | 방 조회만 (WebSocket `ping`은 대기실 기록에 반영 안 됨) |
| 30초 기준에서 버틸 수 있는 누락 | 29번 | **1번** |

조회 주기가 15초면 조회를 1번만 놓쳐도 공백이 30초가 되어 기준선에 닿고, 연속 2번 놓치면 45초가 되어 확실히 퇴장된다. 모바일 네트워크의 순간 끊김이나 요청 지연 한 번이 곧 퇴장이 되는 구조였다.

**가설을 부하테스트로 확인했다.** k6로 실제 Unity 클라이언트와 같은 동작을 재현했다. WebSocket 연결, 10초 `ping`, 15초 방 조회를 하고, `DROP_RATE` 확률로 조회 한 번을 건너뛰게 해 네트워크 흔들림을 흉내 냈다. 응답 명단에서 내가 빠지면 "억울한 퇴장"으로 셌다.

조건: 방 50개 × 4명(200명), 5분 대기

| 실행 | 기준 시간 | 조회 누락률 | 억울한 퇴장 | 계산상 예상 | 방 조회 p95 |
| --- | --- | --- | --- | --- | --- |
| A0 기준선 | 45초 | 0 | 0 / 200 | 0 | 14ms |
| **A1 장애 재현** | **30초** | 0.1 | **31 / 200 (15.5%)** | 약 17% | 14ms |

- 서버는 전혀 느리지 않았다(p95 14ms, HTTP 실패 0%). **원인은 서버 성능이 아니라 조회 주기 대비 짧은 기준 시간이라는 설계 문제**였다.
- 실측이 확률 계산과 맞았다. 연속 2번 누락 확률은 0.1² = 1%이고, 5분 동안 조회가 약 19번이므로 한 명이 한 번이라도 걸릴 확률은 1 − 0.99¹⁹ ≈ 17%다. 실측은 15.5%였다.

### 3. 의사 결정 과정

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| ① 기준 시간을 45초로 늘리기 | 설정 한 줄, 클라이언트 변경 없음, 즉시 적용 | 진짜 끊긴 사람을 내보내는 시간도 30초에서 45초로 늦어짐. 확률을 줄일 뿐 구조는 그대로 |
| ② WebSocket `ping`(10초)도 대기실 접속 기록으로 남기기 | 근본 해결. 기록이 HTTP 조회와 분리되고 주기도 10초로 짧아짐 | 실시간 모듈과 대기실 모듈을 함께 수정해야 하고 검증 범위가 넓음 |
| ③ 대기실 조회를 다시 1초 폴링으로 | 확실히 해결 | 요청 수 15배. WebSocket 도입 목적에 역행 |

**결정: 단기에는 ①로 바로 막고, ②를 근본 해결로 예정했다.**

- 실제 사용자가 튕기고 있어서 가장 빨리 적용할 수 있는 ①이 우선이었다.
- 45초는 "15초 조회를 연속 2번 놓쳐도 버틴다"는 근거로 정했다. 진짜로 끊긴 사람이 나가는 데 15초가 더 걸리는 건 대기실에서 감수할 만하다고 판단했다.
- ①이 실제로 충분한지는 감이 아니라 같은 테스트로 검증하기로 했다.

### 4. 개선 방법 및 수치

`application.properties`의 `mafia.lobby.idle-timeout-seconds`를 30에서 45로 바꿨다(커밋 `2f27052`). 같은 시나리오로 다시 측정했다.

| 실행 | 기준 시간 | 조건 | 억울한 퇴장 | 계산상 예상 |
| --- | --- | --- | --- | --- |
| A1 (개선 전) | 30초 | 200명, 누락 0.1 | 31 / 200 (15.5%) | 약 17% |
| **A2 (개선 후)** | **45초** | 200명, 누락 0.1 | **4 / 200 (2.0%)** | 약 2% |
| A3 | 45초 | 600명 + 로비 100명, 누락 0.05 | 1 / 600 (0.17%) | 약 0.2% |
| A3 stress | 45초 | 600명 + 로비 300명(0.5초마다 새로고침), 누락 0.05 | 0 / 600 | 약 0.2% |

- 같은 조건(누락 0.1)에서 퇴장이 **15.5%에서 2.0%로 약 8분의 1**이 됐다.
- 누락률 0.05에서는 600명 중 0~1명으로 실사용에 문제없는 수준이었다.
- **서버 부하는 퇴장에 영향을 주지 않았다.** 로비 새로고침을 세게 걸어 서버 전체 HTTP p95가 500ms까지 올라간 상황에서도 방 조회는 p95 12ms를 유지했고 퇴장도 늘지 않았다. 퇴장은 오직 "조회 누락 횟수 × 15초 > 기준 시간"으로 결정됐다.
- 다만 **0은 아니다.** 45초에서는 연속 3번 누락(공백 60초)부터 퇴장된다. 기준을 늘리는 방식은 확률만 낮출 뿐이라는 것도 수치로 확인됐다.

### 5. 결과 및 배운 점

**결과**
- 실제로 겪은 장애를 부하테스트로 재현해 원인이 설계(15초 HTTP 조회에만 의존)라는 걸 수치로 증명했다.
- 45초 조정으로 억울한 퇴장을 약 8분의 1로 줄였고, 현실적인 누락률에서는 거의 0이 됐다.
- **다음 단계**: WebSocket `ping`(10초)을 대기실 접속 기록에도 반영한다. 기록 주기가 HTTP와 분리되므로 이후 같은 시나리오(누락 0.1)에서 퇴장이 0이 되는지 확인하고, 기준 시간을 다시 줄일 수 있는지 측정할 예정이다.

**배운 점**
- **한 곳을 바꾸면 그 값에 기대던 다른 곳을 같이 봐야 한다.** WebSocket 도입으로 조회 주기가 바뀌었는데, 그 주기를 전제로 정한 기준 시간이 그대로 남아 있었다.
- **확률로 예상하고 측정으로 확인하면 결과를 설명할 수 있다.** 누락률과 조회 횟수로 계산한 예상(17%, 2%, 0.2%)이 실측과 맞아서, "운이 나빴다"가 아니라 "구조상 이만큼 생긴다"고 말할 수 있었다.
- **임시 대응과 근본 해결을 구분해야 한다.** 45초는 효과가 있었지만 0이 아니었다. 수치가 있으니 근본 해결이 왜 필요한지도 근거를 갖고 말할 수 있었다.

## B. 방 목록 조회의 N+1 Redis 호출

### 1. 문제 상황

A의 스트레스 테스트(로비 300명이 0.5초마다 방 목록 새로고침) 중에 서버 전체 응답이 느려졌다.

| 지표 | 값 |
| --- | --- |
| 전체 HTTP p95 / p99 / max | 499ms / 668ms / 1,024ms |
| 방 목록(`GET /rooms`) 중앙값 | 125ms |
| 같은 시간 방 상세(`GET /rooms/{id}`) p95 | **12ms** |
| 처리량 | 목표 약 600 req/s 중 468 req/s |

같은 서버, 같은 Redis인데 **방 목록만 10배 이상 느렸다.** 방은 150개뿐이었다.

### 2. 원인 분석

**코드**: 방 목록은 방 ID 목록을 읽은 뒤 방마다 따로 읽었다.

```java
Set<String> roomIds = roomRepository.findAllRoomIds();   // SMEMBERS 1번
return roomIds.stream()
        .map(Long::valueOf)
        .map(roomRepository::findById)                    // 방마다 GET 1번 (직렬)
        ...
```

방이 N개면 요청 1번에 Redis를 **N+1번 직렬 왕복**한다. DB에서 흔히 말하는 N+1 문제가 Redis에서 생긴 것이다.

**측정으로 확인했다.** 방 수만 바꿔 가며 같은 부하(최대 100명, 1초마다 새로고침)를 주고, 테스트 앞뒤로 Redis `INFO commandstats`를 찍어 명령 횟수를 비교했다. 대기실 검사는 꺼서 다른 기능의 호출이 섞이지 않게 했다.

| 방 수 | 동시 사용자 | GET ÷ SMEMBERS | 목록 avg | p95 | p99 | req/s | 초당 Redis GET |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 100 | 100 | **100.0** | 166ms | 224ms | 260ms | 52.8 | 약 5,200 |
| 500 | 100 | **500.0** | 320ms | 595ms | 682ms | 48.3 | 약 22,900 |
| 1000 | 100 | **1000.0** | 912ms | 1,485ms | 1,691ms | 34.7 | 약 31,700 |
| 1000 | 4 | 1000.0 | 260ms | 283ms | 292ms | 1.9 | |

- **요청 1번당 GET이 정확히 방 수만큼** 호출됐다. N+1이 숫자로 증명됐다.
- 동시 4명(경쟁 없음)에서도 방 1000개면 260ms가 걸렸다. 왕복 1번 약 0.26ms × 1000번으로, **구조 자체의 비용**이다.
- 동시 100명이 되면 912ms로 3.5배 느려졌다. 요청마다 1000번씩 왕복하니 사용자가 늘수록 Redis 연결이 붐벼 지연이 증폭됐다.
- 100 → 500개 구간은 공유 연결이 명령을 묶어 보내는 효과로 덜 늘었지만(×1.9), 초당 GET 3만 회 부근인 500 → 1000개 구간에서는 비선형으로 나빠졌다(방 2배에 지연 ×2.85).
- 응답이 느려지자 같은 100명이 보내는 요청 수(req/s)도 52.8에서 34.7로 줄었다. 사용자가 기다리고 있다는 뜻이다.

### 3. 의사 결정 과정

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| ① **MGET 한 번으로 읽기** | 코드 변경이 저장소 메서드 1개 + 호출부 1곳. 응답 형식·동작 그대로, 클라이언트 변경 없음 | 방이 수만 개가 되면 MGET 한 번이 커짐 |
| ② 파이프라인(`executePipelined`) | 왕복은 ①처럼 줄어듦 | 같은 효과에 코드가 더 복잡함 |
| ③ 목록 응답 캐시(짧은 TTL) | 호출 자체를 줄임 | 새로 만든 방이 늦게 보임. 무효화 처리 필요. N+1 구조는 그대로 남음 |
| ④ 페이지네이션 / 자료구조 변경 | 방이 아주 많아져도 대응 | API와 Unity 로비 화면까지 바꿔야 하는 큰 변경 |

**결정: ①을 선택했다.**

- 원인이 "왕복 횟수"였으니 왕복을 줄이는 게 정확한 처방이다. 캐시(③)는 증상만 가리고 원인은 남긴다.
- 동작이 바뀌지 않아 기존 클라이언트와 테스트를 그대로 둘 수 있다. 위험이 가장 작고 효과는 가장 직접적이다.
- 현재 규모(방 수백~1000개)에서는 MGET 한 번이면 충분하다. 수만 개 규모가 되면 ④를 검토한다.

### 4. 개선 방법 및 수치

**코드** (`perf/room-list-mget`)

```java
// LobbyRoomRepository: 여러 방을 Redis 왕복 1번으로 읽는다
public List<Room> findAllByIds(Collection<Long> roomIds) {
    if (roomIds == null || roomIds.isEmpty()) return List.of();
    List<String> keys = roomIds.stream().map(id -> PREFIX + id).toList();
    List<Room> rooms = redisTemplate.opsForValue().multiGet(keys);
    if (rooms == null) return List.of();
    return rooms.stream().filter(Objects::nonNull).toList(); // 그 사이 지워진 방은 뺀다
}

// RoomService.getRooms
List<Long> ids = roomIds.stream().map(Long::valueOf).toList();
return roomRepository.findAllByIds(ids).stream()
        .filter(room -> titleMatches(room, normalizedKeyword))   // 검색·복구·변환 순서는 그대로
        ...
```

**테스트**
- `LobbyRoomRepositoryFindAllTest`: MGET을 1번만 호출하고 GET은 호출하지 않는지, 지워진 방(null)은 빠지는지, 빈 목록이면 Redis를 호출하지 않는지 확인한다.
- `RoomServiceRoomListTest`: 전체 목록·제목 검색 결과가 예전과 같은지, 방을 한 번에 읽는지(`findById` 0회), ID 목록에만 남은 지워진 방은 빠지는지 확인한다.

**수치** (방 1000개)

| 조건 | 개선 전 avg / p95 / p99 | 개선 후 avg / p95 / p99 | 개선 |
| --- | --- | --- | --- |
| 동시 100명 | 912 / 1,485 / 1,691ms | **22 / 33 / 37ms** | p95 **약 45배** |
| 동시 4명 | 260 / 283 / 292ms | **23 / 31 / 38ms** | 약 11배 |
| 처리량 (동시 100명) | 34.7 req/s | **59.5 req/s** | +71% |
| 요청당 Redis 왕복 | 1,001번 (SMEMBERS 1 + GET 1000) | **2번** (SMEMBERS 1 + MGET 1) | |
| 약 6분간 Redis 호출 | GET 11,116,500번 | GET 0번, MGET 20,760번 | |

`MGET` 횟수(20,760)가 `SMEMBERS` 횟수(20,760)와 정확히 같다. 목록 요청 1번당 MGET 1번이다.

### 5. 결과 및 배운 점

**결과**
- 방 1000개·동시 100명에서 목록 조회 p95를 **1.49초에서 33ms로** 줄였다.
- **이제 동시 사용자 수와 상관없이 응답 시간이 같다**(4명 23ms, 100명 22ms). 개선 전에는 4명에서 100명이 되면 3.5배 느려졌다.
- 개선 후 방 1000개(22ms)가 개선 전 방 100개(166ms)보다도 7배 이상 빠르다. 방 수에 비례하던 비용이 사실상 사라졌다.
- 남은 약 22ms는 방 1000개를 역직렬화하고 응답 JSON을 만드는 비용이다. 방이 훨씬 많아지면 페이지네이션으로 줄일 수 있다.

**배운 점**
- **N+1은 DB만의 문제가 아니다.** Redis처럼 빠른 저장소도 왕복을 N번 하면 결국 왕복 횟수가 지연을 결정한다. 한 번 왕복은 0.26ms로 빨라도 1000번이면 0.26초다.
- **응답 시간보다 호출 횟수가 더 확실한 증거다.** 응답 시간은 환경과 동시성에 따라 흔들렸지만(100→500개 구간이 덜 늘어난 것처럼), "요청당 GET = 방 수"는 어떤 조건에서도 정확히 같았다. 원인을 증명할 때는 결정적인 지표를 먼저 잡아야 한다.
- **부하를 걸어 봐야 보이는 문제가 있다.** 이 코드는 기능 테스트를 모두 통과했고, 방이 적은 개발 환경에서는 느린 줄 몰랐다. 원래 A를 보려던 스트레스 테스트에서 우연히 드러났다.
- **고치기 전에 기준선을 남겨야 한다.** 개선 전 수치를 방 수·동시 사용자별로 남겨 둔 덕분에 개선 효과를 같은 조건으로 비교할 수 있었다.

**멀티서버·확장 시 고려**

| 상황 | MGET 영향 | 대응 |
| --- | --- | --- |
| 서버 여러 대 + Redis 1대 (팀의 멀티서버 계획) | 문제없음. 일관성은 오히려 좋아짐 | 필요 없음 |
| 방이 수만 개 | MGET 한 번이 커져 Redis를 잠깐 붙잡음 | 나눠 읽기(예: 500개씩) 또는 페이지네이션 |
| Redis Cluster로 전환 | 키가 다른 슬롯에 흩어져 날것 MGET은 `CROSSSLOT` 에러 | 클라이언트의 슬롯별 분할에 맡기거나 해시 태그 사용. 전환 시 테스트 필수 |

- **서버 여러 대 + Redis 1대**: 방 상태는 처음부터 Redis에 있고 서버는 상태를 들고 있지 않다. 어느 서버가 요청을 받든 같은 키를 SMEMBERS → MGET으로 읽으므로 결과가 같다. 서버 메모리 캐시를 두지 않아 서버끼리 어긋날 일도 없다.
  - Redis는 명령을 하나씩 처리하므로 MGET 1번은 그 순간의 스냅샷이다. 예전처럼 GET을 1000번 나눠 보내면 그 사이 다른 서버가 방을 바꿀 수 있어, 목록 하나에 시점이 다른 방이 섞였다.
  - SMEMBERS와 MGET 사이에 다른 서버가 방을 지우면 MGET에서 null이 온다. 이 경우는 걸러내도록 구현하고 테스트(`그_사이_지워진_방은_결과에서_뺀다`)로 확인했다. 그 사이 새로 생긴 방은 다음 새로고침에 보이고, `room.created` 신호로도 알린다.
  - Redis 부하는 서버 대수가 아니라 전체 요청 수로 정해진다. 서버를 늘려도 요청당 왕복은 2번 그대로다.
- **방이 아주 많아질 때**: MGET은 키 수에 비례하는 명령이라 수만 개를 한 번에 읽으면 그동안 다른 명령이 잠깐 기다린다. 이때는 나눠 읽거나, API를 페이지 단위로 바꾼다.
- **Redis Cluster**: 클러스터는 키를 해시 슬롯으로 나눠 여러 노드에 저장한다. `room:1`, `room:2`처럼 슬롯이 다른 키를 한 MGET에 넣으면 Redis가 거부한다.
  - Spring Data Redis(Lettuce)의 클러스터 연결은 다중 키 명령을 슬롯별로 나눠 각 노드에 보내고 결과를 합친다. 그래서 코드는 그대로 동작할 가능성이 높고, 왕복도 방 수가 아닌 노드 수만큼이라 N+1보다 훨씬 적다. 다만 전환할 때 실제 클러스터 환경에서 테스트로 확인해야 한다.
  - 키를 `room:{lobby}:1`처럼 해시 태그로 묶으면 같은 슬롯에 모여 MGET 1번이 된다. 대신 방 데이터가 한 노드에 몰리는 단점이 있다.
  - 현재 운영은 Redis 1대(`deploy/docker-compose.prod.yml`)라 해당하지 않는다. 방 수나 메모리가 한계에 가까워질 때 검토한다.
